### 1.1 Install the .NET SDK

Rider is only an editor. It does not ship a compiler; it drives the `dotnet` toolchain,
which has to exist on the machine separately.

```bash
brew install --cask dotnet-sdk
```

This will prompt for the macOS account password — a `--cask` install writes to
`/usr/local/share/dotnet`, which is outside Homebrew's own prefix. The Homebrew cask is
currently **.NET SDK 10.0.401**, which is what `02-tech-stack-and-architecture.md`
specifies (.NET 10 is the current LTS).

Verify:

```bash
dotnet --version        # expect 10.0.4xx
dotnet --list-sdks      # confirms the install location
```

Then point Rider at it: **Settings → Build, Execution, Deployment → Toolset and Build**.
Rider normally auto-detects the SDK; if it does not, the path is `/usr/local/share/dotnet`.

### 1.2 EF Core CLI tool

Needed from step 5 onwards for migrations. Installing it now keeps step 5 about the
database instead of about tooling.

```bash
dotnet tool install --global dotnet-ef
dotnet ef --version
```

`dotnet ef` is a **global tool** — a separate NuGet package installed into
`~/.dotnet/tools`, not part of the SDK. It is a design-time tool only: it reads the
`DbContext` to generate migration C# files. It is never present at runtime and never
ships in the Docker image.

## 2. A dedicated git repository

Today `/Users/turzo/Work/MISL` is a **subfolder of the `/Users/turzo/Work` repo**, which
contains unrelated projects (RideX, SalesBot, ToDo_list…). That repo's history is useless
as a submission artifact.

The PDF grades *"meaningful commits showing the development progress"* — so the history
being clean, readable, and only about this project is worth actual marks.

From a terminal:

```bash
cd /Users/turzo/Work/MISL
git init
git branch -M main
```

Nesting a repo inside another repo is legal in git: the parent simply sees `MISL/` as an
untracked directory and ignores its contents. The inner repo is fully independent — its
own history, its own remote, its own branches. (This is *not* a submodule; a submodule
would require the parent to record a pointer to it. We want no relationship at all.)

### 2.1 `.gitattributes`

Create `.gitattributes` in the `MISL/` root (the folder, not in `backend/` or `frontend/`):

```
* text=auto
```

Normalises line endings to LF **in the repository**, while checking out whatever the local
platform prefers. Not strictly required now that development is single-machine, but the
graders will clone this on an unknown OS, and a `.gitattributes` costs one line.

### 2.2 `.gitignore`

From the terminal, generate the .NET one and append frontend entries:

```bash
cd /Users/turzo/Work/MISL
dotnet new gitignore
```

Then edit `.gitignore` to append:

```
# Frontend
node_modules/
dist/
frontend/.vite/

# macOS
.DS_Store

# Local secrets
*.env
appsettings.Development.local.json
```

What must never be committed, and why:
- `bin/`, `obj/` — build output. Platform- and machine-specific, regenerated by every
  build, and large. Committing them is the classic beginner tell.
- `node_modules/` — reconstructible from `package-lock.json`, and tens of thousands of files.
- `.env` / local secrets — credentials in git history are permanent even after deletion.

`package-lock.json` **is** committed: it pins exact transitive dependency versions so
`npm ci` inside Docker reproduces the same tree the app was developed against.

## 3. Backend scaffold via Rider

The PDF mandates the top-level layout, so the project sits inside `backend/`.

**In Rider:**

1. **File → New → Project**
2. Select **ASP.NET Core Web API** (not Minimal API; see why below)
3. Configure:
   - Project name: `Ledger.Api`
   - Location: `/Users/turzo/Work/MISL/backend`
   - Framework: **.NET 10** (the default)
4. Finish
5. Rider will automatically create `backend/` and place the project inside it

Rider will scaffold a solution file (`Ledger.sln`) at the root of `backend/` and the project
folder `Ledger.Api/` beneath it. (On the CLI this would be `dotnet new webapi --use-controllers`.)

### 3.1 Why "Web API" and not "Minimal API"

Since .NET 8, both options exist. The new template default is **Minimal APIs** — endpoints
declared as lambdas directly in `Program.cs`. 

Choosing **ASP.NET Core Web API** (the classic controller style) is deliberate:
- The architecture in doc 02 is Controller → Service → DbContext. Controllers make that
  boundary a *file boundary*, not a convention.
- Attribute-based routing and `[Authorize(Roles = "Admin")]` on a class or method is the
  clearest way to show role-based authorization in the viva.
- Model binding + `[ApiController]` validation behaviour is automatic.

Minimal APIs are the faster, lower-ceremony choice for a small service, and are worth
naming as the road not taken — they would have made `Program.cs` long and put routing,
validation, and business calls in one file.

### 3.2 Immediate cleanup

Once the project is open in Rider, delete the weather sample:

1. In the project tree, right-click `Controllers/WeatherForecastController.cs` → Delete
2. Delete `WeatherForecast.cs` from the project root the same way

### 3.3 What the scaffold generates

| File | What it is |
|---|---|
| `Program.cs` | The entire startup: build the DI container, build the middleware pipeline, run Kestrel. .NET 6+ has no `Startup.cs`; everything is here. |
| `Ledger.Api.csproj` | The project file — target framework, NuGet `PackageReference`s. MSBuild reads this to build. |
| `appsettings.json` | Base configuration, committed. **No secrets.** |
| `appsettings.Development.json` | Overrides applied when `ASPNETCORE_ENVIRONMENT=Development`. Later keys win. |
| `Properties/launchSettings.json` | **Local dev only** — ports and env vars used by Rider Run. Not read in Docker, not published. |
| `Ledger.Api.http` | Rider scratch file for firing requests at the API. Keep — it replaces Postman. |

## 4. Frontend scaffold via CLI

Frontend tooling (Node/npm/Vite) has no IDE integration in Rider comparable to the .NET
side; the CLI is the natural home. From a terminal:

```bash
cd /Users/turzo/Work/MISL
npm create vite@latest frontend -- --template react-ts
cd frontend
npm install
```

Do not run `npm run dev` yet — that will be done at commit time to verify.

**Why Vite and not Create React App:** CRA was formally deprecated by the React team in
February 2025. Vite is the current default — dev server startup is near-instant because
it serves native ES modules without bundling, and it only bundles (via Rollup) for the
production build. That production build is exactly what the nginx container will serve
in step 11.

`--template react-ts` gives TypeScript from the first line. Retrofitting types later is
strictly harder, and on a *money* application, `amount: number` vs `amount: string` is a
distinction that has to be visible in the type system (doc 01 §7.1).

## 9. Viva questions this step answers

1. **Why use Rider instead of the CLI?** Rider is a full .NET IDE with integrated build,
   run, and debugging. The CLI is a toolchain; Rider is an IDE. Both produce identical
   output, but Rider's Run button and integrated database browser are worth explaining.
2. **Why controllers and not Minimal APIs?** The Controller→Service→DbContext boundary
   becomes a file boundary; attribute routing and `[Authorize(Roles=…)]` read clearly.
   Minimal APIs trade ceremony for compactness; we chose clarity.
3. **Why Vite and not Create React App?** CRA was deprecated by React in Feb 2025. Vite
   serves native ESM in dev (instant startup, no bundling) and Rollup-bundles for
   production, which is what the nginx container will serve.
4. **What is in `Program.cs`?** Two phases: register services into the DI container
   (`builder.Services`), then compose the middleware pipeline (`app.Use…`). Order of
   the second phase is behaviour, not style — see doc 02 §2.1.
5. **Why is `launchSettings.json` not used in Docker?** It is a local dev-tooling file
   read by Rider's Run button. In a container the process is launched directly and
   configured by environment variables (`ASPNETCORE_URLS`, etc.).
6. **Why is `obj/`/`bin/` ignored but `package-lock.json` committed?** The first is
   regenerated build output; the second is a reproducibility lock that `npm ci` depends on.
   It ensures the Docker build reproduces the exact dependency tree.
7. **Why does this project have its own git repo inside `/Users/turzo/Work`?** So the
   commit history submitted is only this project's development progress, which is itself
   graded. The parent repo's history is noise.
8. **What is `dotnet ef` and does it ship to production?** A design-time global tool that
   reads the `DbContext` to generate migration files. Never at runtime, never in the
   image. It saves tedious SQL hand-writing.
